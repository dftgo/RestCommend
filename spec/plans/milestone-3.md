# תוכנית — Milestone 3: זרימת המלצות מלאה עם חוזי נתונים מבוקרים

מבוסס על MILESTONES 1.2, PRD 0.5, ARCHITECTURE 0.3 (כולל ADR-1 עד ADR-5), DESIGN 0.3 והקוד של Milestones 1–2 (apps/web).

## מטרה בקצרה
להפוך את בקשת החיפוש שנבנית במסך 04 לתוצאות אמיתיות־במבנה: שרת מקומי מקבל את הבקשה, בודק אותה, מפיק מועמדים מ**נתוני דוגמה (fixtures)** מסומנים, מעריך כל פרמטר (מתאים / לא ידוע / לא מתאים), מדרג בקוד דטרמיניסטי ומחזיר תשובה מאומתת. האפליקציה מציגה את מסך 05 ״ההמלצות שלכם״ עם הסברים, חריגות, מקורות, שיתוף והמלצות נוספות.

אין עדיין OpenAI (Milestone 4) ואין Google Places / Routes (Milestone 5). כל נתוני ההדגמה — מסעדות, מחירים, דירוגים וזמני נסיעה — מסומנים בבירור כלא אמיתיים.

## מה לא בונים כאן
- אין קריאה ל־OpenAI, ל־Google או לכל שירות חיצוני; אין צורך בחשבונות או במפתחות של ספקים.
- אין פתרון כתובת ידנית (LOCATION_UNRESOLVED נוסף ב־Milestone 5); במסלול נסיעה הכתובת / המיקום נשלחים לשרת אך אינם משמשים לחישוב.
- אין שמירה במועדפים: **הלב אינו מוצג בכרטיס עד Milestone 6** (כדי לא להציג כפתור שלא עובד).
- אין הגבלת קצב (Milestone 7), אין פריסה לאינטרנט, אין endpoints של `/v1/places/resolve` ו־`/v1/favorites/refresh` (Milestones 5–6).
- אין שמירת היסטוריית חיפושים; תוצאות החיפוש נשמרות בזיכרון בלבד.

## מבנה הקוד אחרי ה־Milestone

```
apps/web            האפליקציה (קיים)
apps/api            שרת Node + Express (חדש)
packages/contracts  חוזי API משותפים: סכמות Zod + טיפוסים + קטלוגים + בניית טקסט השיתוף (חדש)
```

- `package.json` בשורש: workspaces `apps/*` + `packages/*`.
- `packages/contracts` נצרך כקוד TypeScript ישירות (בלי שלב build): Vite מקמפל אותו באפליקציה, ו־`tsx` מריץ אותו בשרת.
- **הרצה בפיתוח:** `npm run dev` בשורש מריץ במקביל את השרת (פורט 8787) ואת Vite (5173), באמצעות `concurrently`. Vite מעביר את כל הבקשות ל־`/v1/*` לשרת (proxy) — גם ב־`dev` וגם ב־`preview` — כך שהקישור הזמני לטלפון ממשיך לעבוד עם כתובת אחת.
- `npm run serve` = build של האפליקציה + השרת + `vite preview` (4173).
- `npm test` ו־`npm run lint` בשורש רצים על כל החבילות.
- `.claude/launch.json` מתעדכן כך ש־`web-dev` ו־`web-serve` מריצים גם את השרת.
- Service Worker: `/v1/*` מוחרג מ־navigateFallback ואינו נשמר ב־cache — חיפוש דורש רשת.

**תלויות חדשות (גרסאות יציבות אחרונות בזמן הבנייה, נעולות במדויק):** `zod` (contracts, api, web), `express` + `@types/express` (api), `tsx` (api), `concurrently` (שורש, פיתוח). בדיקות ה־API רצות עם Vitest מול השרת בפורט אקראי באמצעות `fetch` — בלי ספרייה נוספת.

## הגדרות ומפתח גישה (.env)

לפי CLAUDE.md: אצור `.env.example` בשורש עם שמות בלבד, ואעתיק אותו פעם אחת ל־`.env`. **אני לא קורא את `.env`.**

```
# Shared access key: any long made-up value. Put the SAME value in both lines.
APP_ACCESS_KEY=
VITE_APP_ACCESS_KEY=
# Optional (defaults in code): DEMO_SCENARIO, SEARCH_TIMEOUT_MS, MAX_CANDIDATES, API_PORT
```

- הקובץ אחד, בשורש; Vite קורא ממנו (`envDir` לשורש), והשרת טוען אותו בהפעלה. משתנה שכבר קיים בסביבה גובר על הקובץ.
- אם `APP_ACCESS_KEY` חסר — השרת לא עולה ומדפיס הודעה ברורה (בלי ערכים).
- **מה תצטרך לעשות:** למלא ב־`.env` סיסמה מומצאת כלשהי, זהה בשתי השורות. זה לא מפתח של ספק ואין צורך בחשבון. הבדיקות העצמיות שלי בזמן הבנייה ירוצו עם מפתח בדיקה זמני שמועבר בפקודת ההרצה, כך שהבנייה לא תיעצר; לפני ״הרץ כדי שאבדוק״ אזכיר לך למלא.

## החוזה — `packages/contracts`

מקור אחד לסכמות Zod ולטיפוסים שנגזרים מהן; השרת והאפליקציה משתמשים באותם קבצים.

**קטלוגים** (מועברים מ־`apps/web/src/catalogs` — מזהה + תווית עברית; השרת צריך את התוויות להסברים ובהמשך למודל): סוגי אוכל, תזונה, אזורים, תקציב, כשרות, אווירות, זמני נסיעה, מסלולי חיפוש. קובצי הקטלוג באפליקציה יייבאו מכאן, בלי שינוי בממשק.

**בקשה — `SearchRequestSchema`** (הצורה שנבנתה ב־Milestone 2, עוברת לכאן לפי ADR-5):
- אובייקטים קפדניים (strict): שדה לא מוכר — למשל `name` — נדחה כ־VALIDATION_ERROR.
- 1–10 משתתפים; tokens בפורמט `p1..p10` ללא כפילויות; כל טקסט חופשי עד 200 תווים; כתובת עד 200.
- מזהי קטלוג בלבד; עד שתי אווירות; ״לא משנה״ בלעדי.
- `travel_time` ⇒ חובה `origin` + `maxTravelMinutes`, אסור `areaIds`; `areas` ⇒ חובה לפחות אזור אחד, אסורים `origin` ו־`maxTravelMinutes`.
- `visitAt` בצורה `{ local, timeZone: 'Asia/Jerusalem', utc }`; `excludedRestaurantIds` עד 100.

**תגובה — `RecommendationsResponseSchema`:**
```ts
{
  requestId: string
  dataSource: 'demo' | 'live'          // 'demo' throughout Milestone 3
  searchedAt: string                    // ISO
  restaurants: Restaurant[]             // 0..5, already ranked
  fewerResultsReason: 'fewer_than_five' | 'none_found' | 'no_more' | null
  publicShareText: string
  sources: { id: string; title: string; url: string; retrievedAt?: string }[]
}

Restaurant {
  restaurantId: string
  name: string                          // includes branch when relevant
  city: string                          // used by the share text
  address: string
  link: { url: string; kind: 'official_site' | 'alternative' } | null
  priceEstimate: { min: number; max: number; currency: 'ILS'; sourceIds: string[] } | null
  travelEstimate?: { minutes: number; note: string } | null   // travel_time mode only
  matchSummary: { mismatchCount: number; unknownCount: number }
  parameters: ParameterResult[]         // every active parameter and its status
  deviations: ParameterResult[]         // status = mismatch (subset, for display)
  uncertainties: ParameterResult[]      // status = unknown (subset, for display)
  perParticipantReasons: { token: string; text: string }[]
  groupReason: string
  ratingsBySource: { sourceName: string; value: number; scale: number; reviewCount?: number; url?: string }[]
  sourceIds: string[]
}

ParameterResult {
  param: 'budget' | 'kosher' | 'atmosphere' | 'area' | 'travel_time' | 'food' | 'diet' | 'opening_hours'
  token?: string                        // for food / diet
  status: 'match' | 'unknown' | 'mismatch'
  reason: string                        // Hebrew, no names
  sourceIds: string[]
}
```
- כל URL חייב להיות `https:` (חוסם `javascript:` וכדומה).
- אין שדות תמונה, חניה או שמות משתתפים.

**שגיאות:** `{ error: { code } }` עם הקודים UNAUTHORIZED (401), VALIDATION_ERROR (400), PROVIDER_UNAVAILABLE (503), SEARCH_TIMEOUT (504), RATE_LIMITED (429, מוגדר כבר בחוזה; ההגבלה עצמה ב־M7), LOCATION_UNRESOLVED (מוגדר; בשימוש ב־M5).

**טקסט השיתוף — רשימת שדות מותרת:** `toPublicShareItem(restaurant)` בוחרת **רק** שם, עיר, הסבר קבוצתי וקישור; `buildPublicShareText(visitAt, items, dataSource)` בונה את הטקסט בפורמט של DESIGN 1.6 (״המלצות למסעדה ליציאה ב־29.10.2026, 20:00״, ואז מסעדות ממוספרות). השרת משתמש בה ל־`publicShareText` של כל תשובה, והאפליקציה משתמשת **באותה פונקציה** כדי לבנות טקסט אחד לכל המסעדות שמוצגות כרגע (כולל ״המלצות נוספות״, במספור רציף). בנתוני דוגמה נוספת שורה: ״נתוני דוגמה — לא מסעדות אמיתיות״.

## השרת — `apps/api`

שרשרת לפי ARCHITECTURE 2.1. בשלב הזה WebResearch מוחלף בספק דוגמה; PlaceResolver ו־RouteEnrichment עדיין לא קיימים.

```
POST /v1/recommendations
  AccessCheck → InputValidation → SearchOrchestrator

```

### ממשק ספק המחקר (התפר ל־Milestone 4)
הספק מקבל את הבקשה ואת רשימת ההחרגות, ומחזיר עד `MAX_CANDIDATES` מועמדים. לכל מועמד עובדות בלבד, כל אחת עם מקור או ״לא ידוע״: סוגי מטבח ומילות מפתח מהתפריט, מחיר משוער לאדם (טווח), כשרות (`certified` / `no_pork_seafood` / `serves_pork_or_seafood` / `unknown`), אווירות (רשימה או לא ידוע), מנות צמחוניות / טבעוניות (`yes` / `no` / `unknown`), אזור, שעות פתיחה לפי ימים (או לא ידוע), דירוגים לפי מקור, קישור, ובמסלול נסיעה — זמן נסיעה. **הספק אינו מחליט על התאמה או דירוג** — זה תפקיד ה־MatchEvaluator וה־Ranker, כך שב־M4 מחליפים רק את הספק.

### נתוני הדוגמה
- כ־20 מסעדות **בדויות**, שמן מתחיל ב״דוגמה:״ (למשל ״דוגמה: טרטוריה על הים״), מזהים `demo-...`. קישורים ומקורות רק לכתובות `https://example.com/...` (דומיין שמיועד לדוגמאות) — אף קישור אינו נראה כמו מסעדה אמיתית.
- פיזור: תל אביב–יפו ~7, גוש דן ~5, חיפה והקריות ~3, ירושלים והסביבה ~3, אילת 2. כך אפשר לראות: חמש תוצאות; ״המלצות נוספות״ פעמיים ואז ״לא נמצאו מסעדות נוספות״ (תל אביב + גוש דן); פחות מחמש (אילת בלבד).
- גיוון מכוון: כשרות עם תעודה / ללא חזיר ופירות ים / לא כשר / לא ידוע; מסעדה שסגורה בשישי בערב ובשבת; מסעדה בלי שעות פתיחה ידועות; מנות טבעוניות לא ידועות; מחירים בכל הטווחים; מסעדה בלי אתר (קישור חלופי); מסעדה בלי שום קישור; מסעדה בלי דירוג.
- **מסלול אזורים:** המועמדים הם מסעדות הדוגמה באזורים שנבחרו (אזור שאין בו מסעדות דוגמה ⇒ אפס תוצאות).
- **מסלול נסיעה:** לכל מסעדה זמן נסיעה **קבוע לדוגמה** (לא תלוי בכתובת); המועמדים הם ה־10 הקרובים. מעל הזמן שנבחר ⇒ חריגה מפורטת. בכרטיס: ״זמן נסיעה: 25 דק׳ (נתוני דוגמה)״.
- **תרחישי בדיקה (`DEMO_SCENARIO`, לפיתוח בלבד):** `normal` (ברירת מחדל, עם השהיה קצרה של ~1.5 שניות כדי שמצב הטעינה ייראה), `empty` (אפס מועמדים), `provider_error` (כשל שירות), `invalid_output` (פלט שבור — נתפס ב־ResponseValidator), `slow` (חורג מתקרת הזמן). התרחיש נקבע בהפעלת השרת; כשתרצה לבדוק מצב שגיאה, אפעיל מחדש עם התרחיש המבוקש.

### MatchEvaluator — כללים (ARCHITECTURE 2.3, 2.7)
פרמטר שסומן ״לא משנה״ אינו פעיל ואינו נספר.

| פרמטר | match | mismatch | unknown |
|---|---|---|---|
| תקציב (אחד לקבוצה) | אמצע טווח המחיר המשוער נמצא באחד הטווחים שנבחרו (גבולות לפי 2.3) | מחוץ לכולם; חומרה = המרחק בש״ח לטווח הקרוב | אין הערכת מחיר |
| כשרות — ״כשר עם תעודה״ | `certified` | `no_pork_seafood` / `serves_pork_or_seafood` | `unknown` |
| כשרות — ״לפחות ללא חזיר ופירות ים״ | `certified` / `no_pork_seafood` | `serves_pork_or_seafood` | `unknown` |
| אווירה (אחד לקבוצה; שתיים = חלופות) | לפחות אחת תואמת | אווירות ידועות ואף אחת לא תואמת | לא ידוע |
| אזור | המסעדה באחד האזורים | מחוץ לאזורים | — |
| זמן נסיעה | ≤ הזמן שנבחר | מעליו; חומרה = הדקות העודפות | אין אומדן |
| אוכל (לכל משתתף, פעיל רק כשיש סוגי אוכל או טקסט לערב) | סוג אוכל משותף, או מילה מהטקסט לערב שמופיעה בתפריט | סוגי המטבח ידועים ואין התאמה (כשנבחרו סוגים) | טקסט בלבד שלא נמצא בתפריט |
| תזונה (לכל משתתף, רק צמחוני / טבעוני) | יש מנות מתאימות | ידוע שאין | לא ידוע |
| שעות פתיחה | פתוחה במועד | (סגורה ⇒ **הוסרה מהמאגר**, לא חריגה) | שעות לא ידועות |

- כמה סוגי אוכל או שתי אווירות = חלופות; אין עונש על כל חלופה שלא נמצאה.
- טקסט הפרופיל (עדיפות נמוכה) אינו פרמטר נפרד ב־M3; בבדיקה עם המודל (M4) הוא ישמש להסבר.

### Ranker — סדר המיון (PRD כללי התאמה 4, ARCHITECTURE 2.7)
מפתח מיון, לפי הסדר:
1. `mismatchCount` עולה — מסעדות ללא חריגה ידועה תמיד ראשונות; התאמות חלקיות נכנסות לחמישייה **רק** אם אין חמש ללא חריגה.
2. `unknownCount` עולה — מאומתת לפני לא מאומתת.
3. חומרת פער כוללת עולה (חריגת תקציב / נסיעה קטנה לפני גדולה).
4. מוניטין יורד — Bayesian adjusted rating של **מקור דירוג אחד עקבי** (בדוגמה: מקור הדוגמה; ב־M5: Google), עם משקל לפי מספר הביקורות. מסעדה בלי דירוג — אחרי המדורגות באותה קבוצה, לא כאפס.
5. `restaurantId` — לשבירת שוויון יציבה.

דירוג גבוה לעולם אינו עוקף את שלבים 1–3. החזרת עד 5; אין השלמה מלאכותית.

### ResponseValidator
- אימות מלא מול `RecommendationsResponseSchema`.
- בדיקות נוספות: עד 5 מסעדות; אין `restaurantId` כפול; אין מסעדה מתוך `excludedRestaurantIds`; כל token בהסברים קיים בבקשה; `deviations` / `uncertainties` תואמים ל־`parameters` ול־`matchSummary`; קישורים ב־https בלבד.
- כשל ⇒ PROVIDER_UNAVAILABLE (״שירות החיפוש אינו זמין כרגע״) עם ניסיון חוזר; **אין** החזרת JSON חלקי. בלוג נרשם רק קוד פנימי `invalid_output`.

### `fewerResultsReason`
- 5 תוצאות ⇒ `null`; 1–4 ⇒ `fewer_than_five`; 0 בבקשה ראשונה ⇒ `none_found`; 0 בבקשת ״המלצות נוספות״ ⇒ `no_more`.
- כשל ספק אינו הופך לעולם ל״אפס תוצאות״.

**ראש המסך:** כותרת; שורה ״{n} מסעדות · לפי התאמה לקבוצה, ואז דירוגים ברשת״; בנתוני דוגמה — פס בולט ״נתוני דוגמה — המסעדות, המחירים, הדירוגים וזמני הנסיעה אינם אמיתיים״ (כמו ״נתוני דוגמה למבנה בלבד״ ב־Wireframe).

**כרטיס מסעדה** (`components/RestaurantCard.tsx`) — כרטיס טקסט, ללא תמונה וללא לב:
- מצומצם: מספר בדירוג, שם, שורת התאמה קצרה וכפתור פתיחה (`aria-expanded`). הכרטיס הראשון פתוח, השאר מצומצמים; פתיחה באותו מסך.
- פתוח, לפי סדר DESIGN 1.6:
  - כתובת.
  - ״מחיר משוער לאדם: 150–200 ₪״ (או ״לא נמצא מידע מאומת״); במסלול נסיעה — ״זמן נסיעה: 25 דק׳״ (+ ״נתוני דוגמה״ בדוגמה).
  - דירוגים: ״{מקור}: 4.5 מתוך 5 · 320 ביקורות״ לכל מקור בנפרד; בלי דירוג — ״לא נמצא דירוג״. אין ״ציון התאמה״ שנראה כמו דירוג גולשים.
  - שורת התאמה: ״ללא חריגות מההעדפות שנבחרו״ / ״ללא חריגות ידועות · {n} פרטים לא אומתו״ / ״{n} חריגות מההעדפות״.
  - ״התאמה לקבוצה״: ההסבר הקבוצתי.
  - ״התאמה לכל משתתף״: אזור נפתח עם שם כל משתתף (ממפת המזהים במכשיר, `<bdi>`) וההסבר שלו.
  - חריגות — כל אחת במפורש: שם הפרמטר (ולמשתתף — גם שמו) + הסיבה, עם סימן ולא רק צבע.
  - פרטים שלא אומתו — ״{פרמטר}: לא נמצא מידע מאומת״.
  - קישור: ״לאתר המסעדה״ / ״לפרטים על המסעדה״ / ״לא נמצא קישור למסעדה״, ו״מקורות״ — רשימת קישורים. כל הקישורים נפתחים בלשונית חדשה (`noopener noreferrer`).
- כל הטקסט נשבר לשורות (כולל כתובות אינטרנט ארוכות) ואין גובה קבוע — הכל נגיש בגלילה גם בטקסט מוגדל. מספרים, מחירים ושעות בבידוד LTR.

**מצבים מיוחדים (נוסחי DESIGN):** פחות מחמש — ״נמצאו {n} מסעדות על בסיס המידע הזמין״; אפס — ״לא נמצאו מסעדות שניתן להמליץ עליהן על בסיס המידע הזמין״ (בלי כפתורי שיתוף והמלצות נוספות); מיצוי — ״לא נמצאו מסעדות נוספות לפי ההגדרות האלה״ (כפתור ההמלצות הנוספות כבר לא פעיל).

**המלצות נוספות:** הכפתור שולח את בקשת ההמשך; טעינה ושגיאה (עם ״ניסיון חוזר״) מוצגות ליד הכפתור; התוצאות הקודמות נשארות. התוצאות החדשות מתווספות מתחת, תחת הכותרת ״המלצות נוספות״, והמספור ממשיך (6, 7, ...). חסימת לחיצה כפולה.

**שיתוף:** ״שיתוף מסעדות והסבר קבוצתי״ בונה טקסט אחד מכל המסעדות שמוצגות (באמצעות פונקציית החוזה) ופותח את חלון השיתוף של המכשיר (`navigator.share`). אם אין תמיכה — העתקה ללוח והודעה ״הטקסט הועתק — אפשר להדביק אותו בכל אפליקציה״. ביטול השיתוף על ידי המשתמש אינו מוצג כשגיאה.

## בדיקות אוטומטיות (Vitest)

**דירוג (`api`) — מול ה־DoD:**
- מסעדה ללא חריגה עם דירוג נמוך קודמת למסעדה עם חריגה ודירוג גבוה.
- חריגה אחת קודמת לשתיים, גם כשלבעלת השתיים דירוג גבוה יותר.
- פרמטר לא ידוע אינו נספר כחריגה, אך מסעדה עם פרמטר לא ידוע מדורגת אחרי מסעדה מאומתת.
- כשיש חמש מסעדות ללא חריגה — אין התאמה חלקית בחמישייה (גם כשיש שבע ללא חריגה ושלוש חלקיות בדירוג גבוה).
- חריגת תקציב קטנה לפני גדולה; מסעדה בלי דירוג אחרי מדורגת באותה קבוצה; התוצאה זהה בכל הרצה.

**הערכת התאמה:** כל שורה בטבלת הכללים; ״לא משנה״ אינו נספר; ״כשר עם תעודה״ עונה גם על האפשרות האמצעית; שתי אווירות כחלופות; סגורה במועד ⇒ מוסרת; שעות לא ידועות ⇒ unknown; גבולות התקציב (100 בדיוק שייך ל״עד 100״).

**נקודת הקצה (בדיקות HTTP מול השרת בפורט אקראי):**
- ללא מפתח / מפתח שגוי ⇒ 401 UNAUTHORIZED, **והספק לא נקרא כלל**.
- קלט לא תקין ⇒ 400 VALIDATION_ERROR: שדה `name`, 11 משתתפים, 3 אווירות, טקסט של 201 תווים, מסלול אזורים עם `origin`, מסלול אזורים בלי אזור, גוף גדול מדי.
- חמש, פחות מחמש ואפס תוצאות, ו־`no_more` בבקשת המשך.
- כשל ספק ⇒ 503; פלט שבור ⇒ 503 בלי תוכן חלקי; חריגה מתקרת הזמן ⇒ 504.
- בקשת המשך עם `excludedRestaurantIds` — אף מסעדה מוחרגת אינה חוזרת, והפרמטרים זהים.
- הלוג (תפוס בבדיקה) אינו מכיל טקסט חופשי, כתובת או הסברים.

**שיתוף (`contracts`):** הטקסט כולל שמות מסעדות, עיר, הסבר קבוצתי וקישורים — ואינו כולל שמות משתתפים, tokens (`p1`...), הסברים אישיים, כתובת מוצא או קואורדינטות; מספור רציף לכל המסעדות המוצגות; פורמט התאריך ״29.10.2026, 20:00״.

**חוזה:** בקשה שנבנית ב־`buildSearchRequest` עוברת את הסכמה בשני המסלולים (הבדיקות הקיימות של Milestone 2 ממשיכות לעבור).

**session באפליקציה:** הוספת batch מוסיפה מתחת; כשל בקשת המשך שומר את כל התוצאות; בקשת המשך מחריגה את כל המוצגות ושומרת את הפרמטרים; חיפוש חדש מחליף את הקודם.

**לקוח:** מיפוי סטטוס/קוד ⇒ הודעה; ניתוק רשת; תקרת 60 שניות; תשובה שאינה עוברת סכמה.
